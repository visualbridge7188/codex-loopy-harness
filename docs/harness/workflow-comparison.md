# 워크플로우 비교 분석 — 기존 스킬 기반 vs 하네스 8-Phase

> **핵심 질문**: "기존 세션 분리형 스킬 체인"과 "하네스 8-Phase 자동화" 중 어떤 방식이 더 좋은가?

---

## 1. 기존 워크플로우 (스킬 체인 방식)

```
┌─────────────────── Session 1: 기획 ───────────────────┐
│                                                         │
│  /office-hour        → 프롬프트/아이디어 논의            │
│       ↓                                                 │
│  /brainstorming      → 이전 작업 기반 브레인스토밍        │
│       ↓                                                 │
│  /grill-with-docs    → 스펙 문서 압박 테스트             │
│       ↓                                                 │
│  /writing-plans      → 플랜 문서 작성                    │
│       ↓                                                 │
│  📄 스펙/플랜 문서 저장                                  │
└─────────────────────────────────────────────────────────┘
                        ↓ 세션 전환
┌─────────────────── Session 2: 개발 ───────────────────┐
│                                                         │
│  @플랜문서                                                  │
│  /writing-plans      → 플랜 기반 이어서 작성              │
│  /subagent-driven    → 서브에이전트 병렬 개발             │
│  /codex:review       → 코드 리뷰                         │
│                                                         │
└─────────────────────────────────────────────────────────┘
                        ↓ 세션 전환
┌─────────────────── Session 3: 유지보수 ───────────────┐
│                                                         │
│  /improve-codebase-architecture  → 리팩토링              │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 특징
- **수동 오케스트레이션**: 각 스킬을 순서대로 직접 호출
- **세션 분리**: 기획/개발/유지보수를 명확히 다른 세션에서 처리
- **컨텍스트 관리**: 세션 전환 시 `@플랜문서`로 컨텍스트 전달
- **유연성**: 필요한 스킬만 선택적 사용 가능

## 2. 하네스 8-Phase 방식

```
┌──────────── 단일 세션 (/team 트리거) ────────────┐
│                                                    │
│  P1: Plan          → Manager가 자동으로 plan.md     │
│  P2: Architecture  → Architect가 자동 설계          │
│  P3: Database      → Supabase 전문가 자동 스키마    │
│  P4: Parallel Impl → Front/Back 병렬 자동 구현      │
│  P5: Test Suite    → Test Writer 자동 테스트 생성   │
│  P6: Static Review → Reviewer 자동 코드 리뷰        │
│  P7: Closed-Loop QA→ QA 최대 5라운드 자동 검증      │
│  P8: Ship & Notify → 자동 배포 + 알림              │
│                                                    │
│  ❌ 15개 에이전트, 10개 훅, Fail-Closed 게이트      │
└────────────────────────────────────────────────────┘
```

### 특징
- **자동 오케스트레이션**: `/team` 하나로 전체 파이프라인 자동 실행
- **단일 세션**: 이론상 한 세션에서 모든 것을 처리
- **검증 게이트**: Hook이 자동으로 정책 시행
- **무거운 구조**: 15 에이전트, 10 훅, 엄격한 파일 경계

## 3. 장단점 비교

| 기준 | 기존 스킬 체인 | 하네스 8-Phase |
|------|---------------|----------------|
| **컨텍스트 관리** | ✅ 세션 분리로 컨텍스트 깔끔 | ⚠️ 단일 세션에 과부하 위험 |
| **유연성** | ✅ 필요한 스킬만 선택 | ❌ 전체 파이프라인 강제 |
| **검증 품질** | ⚠️ 수동 검증 (grill-with-docs) | ✅ 자동 5라운드 QA |
| **설정 오버헤드** | ✅ 스킬만 부르면 됨 | ❌ 15 에이전트 + 10 훅 유지 |
| **기획 품질** | ✅ office-hour + brainstorming + grill 3단계 | ⚠️ Manager 1단계만 |
| **개발 속도** | ⚠️ 수동으로 각 단계 실행 | ✅ 자동 병렬 처리 |
| **디버깅** | ✅ 세션별로 문제 격리 용이 | ⚠️ 파이프라인 중간 실패 시 복잡 |
| **소규모 작업** | ✅ 가볍게 사용 가능 | ❌ 오버엔지니어링 |
| **대규모 작업** | ⚠️ 수동 조정 필요 | ✅ 체계적 관리 |
| **학습 곡선** | ✅ 스킬별 개별 학습 | ❌ 전체 시스템 이해 필요 |

## 4. 핵심 인사이트

### 기존 방식이 더 강력한 부분

1. **기획 단계의 깊이**
   - `/office-hour` → 자유로운 아이디어 논의
   - `/brainstorming` → 창발적 사고 유도
   - `/grill-with-docs` → 스펙에 대한 체계적 압박 테스트
   - → 하네스의 P1(Plan Scaffolding)보다 **훨씬 깊은 기획 품질**

2. **세션 분리의 이점**
   - 컨텍스트 윈도우 한계 회피
   - 각 세션에서 집중적 작업
   - 문서(@플랜문서) 기반 핸드오프가 명시적

3. **선택적 적용**
   - 간단한 작업은 `/office-hour`만으로도 충분
   - 복잡한 작업만 전체 체인 실행

### 하네스 방식이 더 강력한 부분

1. **자동 검증 루프**
   - QA Cycle (최대 5라운드) 자동화
   - Hook 기반 즉시 정책 시행
   - → 기존 방식은 검증이 수동

2. **병렬 개발**
   - Frontend ∥ Backend 동시 구현
   - → 기존 방식도 subagent-driven으로 가능하지만 하네스가 더 체계적

3. **Fail-Closed 보장**
   - 게이트 미통과 시 작업 자동 차단
   - → 기존 방식은 휴먼 에러 가능

## 5. 추천: 하이브리드 3-Phase 워크플로우

**두 방식의 장점을 결합**한 최적의 운용 모델:

```
┌────────────── Phase 1: 기획 (기존 방식 채택) ──────────────┐
│                                                              │
│  Session 1 (기획 전용)                                        │
│  ┌──────────────────────────────────────────────────────┐    │
│  │ 1. /office-hour                                       │    │
│  │    "나는 지금 <프롬프트>를 하려고 해"                    │    │
│  │    → 자유로운 아이디어 논의, 방향성 탐색                  │    │
│  │                                                       │    │
│  │ 2. /brainstorming                                     │    │
│  │    "이 때까지 했던 내용 기반으로 처리해줘"                │    │
│  │    → 창발적 아이디어 확장, 엣지케이스 발굴                │    │
│  │                                                       │    │
│  │ 3. /grill-with-docs                                   │    │
│  │    "이 스펙에 대해서 압박 테스트 해줘"                    │    │
│  │    → 스펙 검증, 약점 식별, 개선사항 도출                  │    │
│  │                                                       │    │
│  │ 4. /writing-plans                                     │    │
│  │    → 최종 플랜 문서 작성                                │    │
│  │                                                       │    │
│  │ 📄 Output: docs/superpowers/plans/YYYY-MM-DD-*.md     │    │
│  └──────────────────────────────────────────────────────┘    │
│                                                              │
│  ✅ 기존 방식의 깊은 기획 품질 유지                            │
│  ✅ 컨텍스트 집중 관리                                        │
└──────────────────────────────────────────────────────────────┘
                            ↓ @플랜문서로 핸드오프
┌────────────── Phase 2: 개발 (하네스 방식 채택) ─────────────┐
│                                                              │
│  Session 2 (개발 전용)                                        │
│  ┌──────────────────────────────────────────────────────┐    │
│  │ @플랜문서                                              │    │
│  │                                                       │    │
│  │ 1. /writing-plans                                     │    │
│  │    → 플랜 기반 구현 계획 세분화                         │    │
│  │                                                       │    │
│  │ 2. /subagent-driven-development                       │    │
│  │    → 하네스의 P2-P4 단계를 스킬 기반으로 실행            │    │
│  │    → Frontend ∥ Backend 병렬 개발                      │    │
│  │    → 각 에이전트 파일 경계 준수                          │    │
│  │                                                       │    │
│  │ 3. /codex:review  (또는 /code-reviewer)               │    │
│  │    → 하네스의 P6 정적 리뷰                              │    │
│  │                                                       │    │
│  │ 4. /qa-cycle                                          │    │
│  │    → 하네스의 P7 자동 QA 루프 (최대 5라운드)             │    │
│  │    → 발견된 이슈 → 전문가 자동 라우팅 → 수정 → 재검증    │    │
│  │                                                       │    │
│  │ 5. Ship (P8)                                          │    │
│  │    → CHANGELOG.md 갱신, 커밋, 푸시                      │    │
│  └──────────────────────────────────────────────────────┘    │
│                                                              │
│  ✅ 하네스의 자동 검증 + 병렬 개발 활용                        │
│  ✅ 스킬 기반이라 필요한 것만 선택적 사용                       │
└──────────────────────────────────────────────────────────────┘
                            ↓ 세션 전환
┌────────────── Phase 3: 유지보수 (공통) ─────────────────────┐
│                                                              │
│  Session 3 (유지보수 전용)                                    │
│  ┌──────────────────────────────────────────────────────┐    │
│  │ /improve-codebase-architecture                        │    │
│  │ → 코드베이스 구조 분석, 리팩토링 제안                    │    │
│  │ → 하네스의 self-improve 스킬과 연계 가능                 │    │
│  └──────────────────────────────────────────────────────┘    │
│                                                              │
│  ✅ 주기적 실행으로 코드 품질 지속 향상                        │
└──────────────────────────────────────────────────────────────┘
```

## 6. 왜 하이브리드가 더 나은가?

| 이유 | 설명 |
|------|------|
| **기획은 깊게** | office-hour → brainstorming → grill-with-docs 3단계가 하네스 P1보다 깊이 있음 |
| **개발은 자동으로** | 하네스의 병렬 개발 + 자동 QA + Hook 게이트를 활용 |
| **컨텍스트는 분리** | 세션 분리로 각 단계의 컨텍스트를 집중 관리 |
| **필요한 것만** | 전체 8-Phase를 강제하지 않고 필요 스킬만 선택 |
| **검증은 자동** | 수동 검증 대신 qa-cycle + hook으로 자동화 |

### 한 줄 요약

> **기획은 기존 스킬 체인의 깊이로, 개발은 하네스의 자동화로, 유지보수는 개별 세션으로.**

## 7. 워크플로우 선택 가이드

| 상황 | 추천 방식 |
|------|----------|
| 간단한 버그 수정 | `/office-hour`만으로 충분 |
| 중간 규모 기능 개발 | 하이브리드 Phase 1-2 |
| 대규모 프로젝트 | 하이브리드 전체 (Phase 1-3) |
| 긴급 핫픽스 | 직접 수정 + `/qa-cycle`만 |
| 코드 품질 개선 | Phase 3만 (`/improve-codebase-architecture`) |
| 스펙/문서 작업 | Phase 1만 (`/office-hour` → `/writing-plans`) |
| 자동화된 프로덕션 | 하네스 `/team` 전체 파이프라인 |

## 8. 실전 운용 체크리스트

### Phase 1 시작 전
- [ ] 작업 범위가 명확한가?
- [ ] 기존 문서/스펙이 있는가? (`@` 참조 준비)
- [ ] 세션 컨텍스트가 충분한가?

### Phase 2 시작 전
- [ ] 플랜 문서가 저장되었는가?
- [ ] 수용 기준(Acceptance Criteria)이 정의되었는가?
- [ ] 파일 경계가 명확한가?

### Phase 3 실행 시
- [ ] 마지막 리팩토링 이후 충분한 변경이 있었는가?
- [ ] 테스트 커버리지가 유지되는가?
- [ ] 성능 메트릭이 기준 이하인가?
